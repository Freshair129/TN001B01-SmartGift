# SmartGift Sales Playbook

## 0. สถานะ ขอบเขต และมติที่ต้องการ

| รายการ | ค่า |
|---|---|
| สถานะ | `draft` — รอ Boss, Sales, Marketing, Product/Sourcing, Operations และ Finance ตรวจ |
| ความซับซ้อน | C-2 — Documentation-Driven Sales Operation |
| ความเสี่ยง | MEDIUM — ข้อความขายหรือการรับปากผิดอาจสร้างความเสี่ยงด้านราคา Claim ระยะเวลา และความเป็นส่วนตัว |
| ใช้กับ | Internal rehearsal และ Controlled Pilot หลัง Owner, Budget และ Account list ได้รับอนุมัติ |
| ไม่ใช่ | สิทธิ์ติดต่อบัญชีจริง, Pricing policy, Quotation authority, Product readiness approval, Legal advice หรือ Production release |

Playbook นี้ช่วยให้ทีมขายเปลี่ยนจากการเริ่มด้วย “อยากได้สินค้าอะไร” เป็น “แคมเปญนี้ให้ใคร เพื่ออะไร และควรดูแลแต่ละกลุ่มอย่างไร” โดยยังเปิดให้ลูกค้าเลือก Tech, Care & Wellness, Taste หรือ Theme อื่นได้ ไม่ถูกล็อกด้วยคำว่า Signature หรือสินค้าเพียงประเภทเดียว

มติที่ขอ:

1. อนุมัติ Sales narrative และ Talk track
2. อนุมัติ Discovery questions และ Qualification gates
3. อนุมัติวิธีส่งต่อจาก Discovery ไป Recipient Matrix และ Offer Route
4. อนุมัติ Objection handling และข้อความต้องห้าม
5. อนุมัติ Funnel handoff, Follow-up discipline และ Rehearsal criteria

ไม่มีการติดต่อ ส่งข้อความ เสนอราคา หรือแก้ระบบใดในรอบเอกสารนี้

## 1. Sales Operating Principles

### SP1 — Start with the recipient

เริ่มด้วย Campaign, ผู้รับ และ Outcome ก่อนสินค้า ลูกค้าสามารถขอดูสินค้าได้ แต่ทีมขายต้องเชื่อมกลับมาว่าสินค้านั้นเหมาะกับผู้รับกลุ่มใดและตอบโจทย์อะไร

### SP2 — One campaign, multiple treatments

หนึ่งแคมเปญมีแกนแบรนด์เดียว แต่แตก Treatment ตาม Recipient Segment ได้ ไม่ต้องบังคับทุกกลุ่มรับของเหมือนกัน

### SP3 — Keep dimensions separate

ห้ามรวม Relationship, Client Segment, Gift Tier, Theme และ Format เป็น Label เดียว เช่น `Signature Tech VIP` เพราะทำให้ลูกค้าถูกล็อกและทีมตรวจเหตุผลไม่ได้

### SP4 — Client owns recipient meaning

ลูกค้าเป็นผู้กำหนดว่าใครคือ Platinum Member, Key Media, Leadership หรือกลุ่มสำคัญ SmartGift ไม่จัดอันดับบุคคลแทนลูกค้า

### SP5 — Choice without chaos

ให้ลูกค้าเลือก Direction 2 Route เป็นค่าเริ่มต้น Route ที่ 3 ใช้เมื่อมีความต่างเชิงกลยุทธ์จริง ไม่โยนรายการสินค้าจำนวนมากให้ลูกค้าออกแบบข้อเสนอเอง

### SP6 — Evidence before promise

ราคา MOQ Lead time Spec Stock Claim Voucher terms และ Sustainability/Health/Food statement ต้องมี Authority และ Validity ก่อนสื่อสารเป็นคำมั่น

### SP7 — Unknown is acceptable

คำตอบ `TBD`, `ยังไม่ทราบ` หรือ `ต้องตรวจ feasibility` ดีกว่าการเดา ทุก Unknown ต้องมี Owner และ Next action

### SP8 — Approval is granular

การชอบแนวคิดไม่เท่ากับอนุมัติราคา การอนุมัติ Matrix ไม่เท่ากับสั่งผลิต และการตอบรับ Proposal ไม่เท่ากับ Won

## 2. Positioning ที่ทีมขายต้องใช้ร่วมกัน

### Master Message

> **SmartGift — เริ่มจากคนรับ ไม่ใช่เริ่มจากของ**

### Commercial Explanation

> เราช่วยแยกผู้รับในหนึ่งแคมเปญตามความสัมพันธ์และความสำคัญ แล้วคัดระดับการดูแล Theme และรูปแบบให้เหมาะกับแต่ละกลุ่ม โดยยังรักษาภาพแบรนด์และการบริหารโครงการเดียวกัน

### Working Offer Message

> **หนึ่งแคมเปญ หลายกลุ่มผู้รับ หลายระดับของขวัญ แต่สื่อสารแบรนด์เดียวกัน**

### สิ่งที่ Positioning นี้ไม่ใช่

- ไม่ใช่การสร้างหลายแบรนด์ย่อยแยก Tech, Care หรือ Taste
- ไม่ใช่การขายว่า SmartGift มีสินค้ามากที่สุดหรือถูกที่สุด
- ไม่ใช่การทำ Personalization จากข้อมูลส่วนบุคคลโดยอัตโนมัติ
- ไม่ใช่คำรับรองว่าสินค้าทุกชิ้นพร้อมขายหรือทำได้ทุกจำนวน
- ไม่ใช่การแทนที่ Procurement, Brand, Legal หรือ Data approval ของลูกค้า

## 3. 30-Second และ 2-Minute Talk Track

### 3.1 30-Second Version

> ปกติหนึ่งแคมเปญมีผู้รับหลายกลุ่ม เช่น สมาชิกหลาย Tier สื่อ แขก หรือผู้บริหาร แต่การเริ่มจากสินค้าเดียวทำให้ของไม่พอดีกับทุกคน SmartGift จึงเริ่มจากการแบ่งกลุ่มผู้รับและวัตถุประสงค์ก่อน แล้วค่อยออกแบบ 2 Route ที่ต่างกันอย่างมีเหตุผล ภายใต้ภาพแคมเปญเดียวกันครับ

### 3.2 2-Minute Version

> เราไม่ได้บังคับว่าถ้าเป็น Signature ต้องเป็นของ Tech หรือถ้าเป็นผู้บริหารต้องได้ชุดแบบเดียวกัน Signature คือระดับการดูแล ส่วน Tech, Care & Wellness, Taste หรือ Lifestyle เป็น Theme ที่เลือกให้เข้ากับผู้รับได้ เราจะเริ่มจาก Campaign Brief แล้วทำ Recipient Matrix ร่วมกัน เช่น Key Media อาจเป็น Signature Care ขณะที่ General Media เป็น Select Work & Welcome ในงานเดียวกัน จากนั้นทีม Product และ Operations จะตรวจสินค้า ราคา จำนวน ระยะเวลา และข้อจำกัดก่อนออก Route ที่เสนอได้จริงครับ

### 3.3 เมื่อผู้ซื้อขอให้สั้นกว่านั้น

> บอกเรา 3 อย่างก่อนก็ได้ครับ: ให้ในโอกาสอะไร มีผู้รับกี่กลุ่ม และต้องใช้วันไหน แล้วเราจะช่วยจัด Direction ให้เห็นภาพก่อนเลือกสินค้า

## 4. Buyer-role Opening

| Buyer role | Opening question | Value frame | สิ่งที่ต้องระวัง |
|---|---|---|---|
| Marketing / Brand | “ในแคมเปญนี้มีผู้รับกี่กลุ่มที่ต้องรู้สึกต่างกัน แต่ยังอยู่ใต้แบรนด์เดียวกันครับ” | แยก Treatment โดย Campaign message ไม่แตก | อย่ารับรอง Brand claim ก่อนเห็น guideline/evidence |
| CRM / Loyalty | “ลูกค้าใช้ชื่อ Tier และกติกาคัดกลุ่มอย่างไรในแคมเปญนี้ครับ” | รักษาภาษาของ Client และ Mapping ต่อ Campaign | อย่าขอ Export รายชื่อสมาชิกในช่วงแรก |
| PR / Corporate Comms | “Media, Creator, Guest และ VIP ในงานนี้ต้องได้รับประสบการณ์ต่างกันตรงไหนครับ” | หลายกลุ่มบน Timeline และภาพงานเดียว | อย่าจัดอันดับ Key Media แทน Client |
| HR / People | “กลุ่มพนักงานใดต้องการ Welcome หรือ Recognition ต่างกันครับ” | Program เดียว หลาย cohort/treatment | อย่าอนุมานสุขภาพ อายุ หรือสถานะจาก PII |
| Procurement | “อะไรต้องล็อกก่อน: จำนวน Spec งบต่อกลุ่ม หรือวันอนุมัติครับ” | Scope ตรวจได้และลดการแก้ Proposal | อย่ารับปากราคา/MOQ จาก Staging data |
| Executive Sponsor | “ความสัมพันธ์ใดสำคัญที่สุด และผู้รับควรรู้สึกอะไรครับ” | จัดงบและความตั้งใจให้พอดีกับความสำคัญ | อย่าสรุปว่า Tier สูงต้องแพงที่สุด |

## 5. Pre-call Gate

ก่อนการติดต่อหรือการประชุมจริง ต้องมีครบ:

- Account อยู่ใน Controlled outreach list ที่ได้รับอนุมัติ
- Account owner ยืนยันช่องทางและฐานการติดต่อ
- ไม่มีข้อพิพาท การค้างชำระ หรือข้อจำกัดที่ยังไม่เคลียร์
- มี Hypothesis ว่าตรงกับ Pilot Play ใด โดยระบุว่าเป็น Hypothesis ไม่ใช่ข้อเท็จจริง
- รู้ว่าบุคคลที่คุยมีบทบาทอะไร แต่ไม่เก็บ PII เกินความจำเป็น
- ใช้ Message/Asset รุ่นที่อนุมัติ
- มี Meeting objective และ Next-step boundary

ถ้าไม่ครบ ให้สถานะ `NOT_AUTHORIZED_FOR_OUTREACH` และส่งกลับ Pilot Owner/Account Owner

## 6. Discovery Agenda

ใช้เวลาและรูปแบบตามที่ Sales Owner อนุมัติ โดยรักษาลำดับนี้:

1. ยืนยันบริบทและวัตถุประสงค์ของการคุย
2. เข้าใจ Campaign / Occasion / Required-by date
3. แยก Recipient relationship และ Client-defined segment
4. เข้าใจ Outcome และระดับ Treatment ที่ต่างกัน
5. เปิด Theme และ Format preference โดยไม่ล็อกสินค้า
6. ตรวจ Budget basis, quantity, approval และ operational constraints
7. สรุป Unknown, Risk และสิ่งที่ต้องตรวจ feasibility
8. ตกลง Next action และผู้รับผิดชอบ

ประโยคเปิด:

> วันนี้ขอเริ่มจากภาพของแคมเปญและคนรับก่อนนะครับ ยังไม่จำเป็นต้องเลือกสินค้าทันที เป้าหมายคือให้เราเห็นว่ากลุ่มไหนควรเหมือนกัน กลุ่มไหนควรต่างกัน แล้วค่อยกลับไปตรวจ Route ที่ทำได้จริง

## 7. Discovery Question Bank

### 7.1 Campaign and Outcome

- ให้ในโอกาสอะไร และเหตุการณ์นี้สำคัญกับองค์กรอย่างไร
- ผู้รับควรรู้สึก จำ หรือทำอะไรหลังได้รับ
- อะไรคือแกนที่ทุกกลุ่มต้องได้รับเหมือนกัน
- อะไรคือความแตกต่างที่ลูกค้าต้องการให้แต่ละกลุ่มรับรู้
- วันใช้งานจริงคือวันใด และวันอนุมัติสุดท้ายคือวันใด
- เคยทำแคมเปญลักษณะนี้หรือไม่ อะไรได้ผลหรือไม่เหมาะ
- มีข้อความหรือภาพใดที่ห้ามใช้หรือไม่

### 7.2 Recipient Relationship and Segment

- ผู้รับเกี่ยวข้องกับองค์กรอย่างไร: Member, Media, Guest, Team, Leadership, Partner หรือ Community
- ลูกค้าเรียกแต่ละกลุ่มว่าอะไร และใครเป็นเจ้าของความหมาย
- เกณฑ์ใดทำให้คนหนึ่งอยู่ในกลุ่มนี้ใน Campaign นี้
- แต่ละกลุ่มมีจำนวนเท่าใด เป็น Actual, Estimate, Range หรือ TBD
- กลุ่มใดต้องการ Treatment ต่างจากกลุ่มอื่น และเพราะอะไร
- มีคนหนึ่งอยู่หลาย Relationship หรือไม่ ถ้ามี เหตุผลหลักที่ได้รับของครั้งนี้คืออะไร
- มีผู้เยาว์ ข้อมูลสุขภาพ หรือ Sensitive data เกี่ยวข้องหรือไม่

ห้ามถามว่า “ใครเป็น VIP บ้าง ส่งรายชื่อมาเลย” ในช่วง Discovery ให้ถามกติกาและจำนวนระดับกลุ่มก่อน

### 7.3 Gift Tier and Treatment

- กลุ่มใดต้องการ Reach, Select, Signature หรือ Bespoke และ Outcome ต่างกันอย่างไร
- ความพิเศษควรมาจาก Packaging, Message, Choice, Personalization, Service หรือ Experience ส่วนใด
- หากงบต้องลด อะไรคือ Minimum treatment ที่ต้องรักษา
- หากต้องทำทุกกลุ่มเหมือนกัน ผลกระทบที่กังวลคืออะไร
- มี Proof, Sample หรือผู้อนุมัติพิเศษสำหรับกลุ่มใดหรือไม่

### 7.4 Theme and Format

- กลุ่มนี้เหมาะกับ Tech, Care & Wellness, Taste, Lifestyle & Travel, Impact, Work & Welcome หรือ Culture & Local เพราะอะไร
- ลูกค้าอยากเปิด 2–3 Theme ให้เลือก หรือมี Theme ที่ต้องตัดออกหรือไม่
- Physical, Voucher/Experience หรือ Hybrid แบบใดเข้ากับพฤติกรรมและการส่งมอบ
- มีข้อจำกัดเรื่องอาหาร สารก่อภูมิแพ้ แบตเตอรี่ กลิ่น ขนาด การเดินทาง หรือสถานที่หรือไม่
- มีคำขอ Sustainability, Health หรือ Impact claim หรือไม่ ใครมีหลักฐานและอนุมัติ

### 7.5 Commercial and Operational

- Budget เป็นต่อคน ต่อ Segment หรือรวม Campaign และสถานะอนุมัติอยู่ขั้นใด
- จำนวนต่อ Segment ยืนยันเมื่อใด และ Buffer ใครเป็นผู้อนุมัติ
- ต้องการใบเสนอราคาเมื่อใด และใครเป็น Commercial approver
- ต้องมี Sample, Artwork proof หรือ Production proof ระดับใด
- ส่ง Bulk, แจกในงาน, ส่งรายบุคคล หรือ Digital delivery
- มีข้อจำกัดพื้นที่ส่งมอบ การจัดเก็บ การประกอบ หรือช่วงเวลาหรือไม่
- การเปลี่ยนจำนวนหรือ Scope หลังอนุมัติจะจัดการอย่างไร

### 7.6 Decision and Approval

- ใครเป็นเจ้าของ Campaign, Budget, Brand, Procurement และ Recipient data
- ใครยืนยัน Segment และ Gift Tier mapping
- ใครเลือก Route และใครอนุมัติราคา
- มีขั้นตอน Vendor onboarding, PO หรือ Contract ใดที่ต้องเผื่อเวลา
- ถ้าไม่สามารถตัดสินใจตามวันเป้าหมาย ต้อง Hold, ลด Scope หรือย้ายวันใช้งานอย่างไร

## 8. Qualification Gate

ไม่ใช้คะแนนสวย ๆ แทน Evidence ให้จัดสถานะตาม Gate:

### `QUALIFIED_FOR_MATRIX`

ต้องมี:

- Campaign objective และ Required-by date
- อย่างน้อย 2 Recipient Segment หรือเหตุผลชัดว่าต้องการ Treatment ต่างกัน
- Client owner ของ Segment/eligibility
- Count หรือ Range พร้อมสถานะ Source
- Budget basis และ Approval path แม้ค่าจริงยังเป็น TBD
- ไม่มี Critical privacy/claim/timeline blocker ที่ไม่รับผิดชอบ

### `NEEDS_DISCOVERY`

ใช้เมื่อโจทย์มีแนวโน้มเหมาะ แต่ Objective, Segment, Count, Budget basis หรือ Approver ยังไม่พอ ต้องระบุคำถามถัดไปและ Owner

### `NO_FIT_FOR_CONTROLLED_PILOT`

ใช้เมื่อ:

- ต้องการสินค้าราคาต่ำสุดรายการเดียวและไม่ต้องแบ่งผู้รับ
- Timeline บังคับให้ข้าม Spec, Sample, Claim หรือ Commercial Gate
- ต้องใช้ Voucher/Impact/Health/Food claim ที่ยังไม่มี Owner/evidence
- ต้องใช้ PII ก่อนมี Data-sharing boundary
- Bespoke scope ไม่มี Feasibility, Timeline หรือ Commercial owner
- ผู้ขอไม่สามารถเข้าถึงผู้ยืนยัน Segment/Budget/Approval ได้

No-fit ไม่ได้แปลว่าปฏิเสธลูกค้าถาวร ให้ระบุเงื่อนไขที่ต้องเปลี่ยนจึงกลับมาประเมินใหม่ได้

## 9. Discovery Note → Recipient Matrix Handoff

หลังประชุม Account Manager ต้องแปลงข้อมูลเป็น Matrix โดยไม่ตีความเกินหลักฐาน:

| Discovery evidence | Matrix field | Rule |
|---|---|---|
| ความสัมพันธ์กับองค์กร | Primary relationship | ใช้ Controlled Vocabulary |
| ชื่อกลุ่มของลูกค้า | Client segment label | คงคำของลูกค้า |
| กติกาคัดกลุ่ม | Eligibility rule | ต้องตรวจซ้ำได้และลูกค้ายืนยัน |
| จำนวน/ช่วงจำนวน | Estimated count | ใส่ Source date และ Actual/Estimate/TBD |
| สิ่งที่ต้องการให้เกิด | Treatment objective | เขียน Outcome ไม่ใช่ชื่อสินค้า |
| ระดับการดูแล | Gift Tier | ใส่ rationale แยก |
| ความสนใจ/ข้อห้าม | Theme preference/exclusion | ไม่ล็อก SKU |
| วิธีส่งมอบ | Format / Delivery | ระบุ Open/TBD ได้ |
| ข้อมูลผู้รับ | Data class | ห้ามคัด PII ลง Matrix |
| การตัดสินใจ | Client approver / status | อ้าง Approval evidence |

Account Manager ส่ง Matrix draft ให้ลูกค้ายืนยันก่อนเปิด Product selection หากลูกค้าแก้ Segment, Tier หรือ Objective ต้องแก้ Version ไม่แก้ทับเงียบ

## 10. Play-specific Sales Motions

### Play A — Member Appreciation

**Trigger:** Anniversary, Tier renewal, Member event, Appreciation campaign

**Opening:**

> แคมเปญนี้สมาชิกแต่ละ Tier ควรรู้สึกต่างกันตรงไหนครับ และมีอะไรที่ทุก Tier ต้องเห็นเป็นภาพเดียวกัน

**ต้องค้นหา:**

- Client-owned Tier label และ eligibility rule
- Cut-off date และ count status
- Treatment difference ระหว่าง Core, Loyal, Top-tier หรือชื่อจริงของ Client
- Theme preference/exclusion โดยไม่ขอข้อมูลส่วนบุคคลเกินจำเป็น
- Voucher geography/expiry/partner readiness ถ้ามี

**CTA:** นัด Recipient Mapping Session และยืนยันผู้ดูแล CRM/Brand/Procurement

### Play B — Launch & Media

**Trigger:** Product launch, Store opening, Press event, Brand activation

**Opening:**

> ในงานนี้ Media, Creator, Guest, Member และ VIP กลุ่มใดต้องได้รับข้อมูลหรือประสบการณ์ต่างกันครับ

**ต้องค้นหา:**

- Client owner ของ Key/General Media definition
- Event date, media kit deadline และ handout flow
- Press message/embargo/required wording
- Treatment ของ Media เทียบ Guest/VIP
- Portability, event logistics และ on-site contingency

**CTA:** ส่ง Event date, audience count/Range และ approval timeline เพื่อ Draft Matrix

### Play C — Employee Welcome & Recognition

**Trigger:** Onboarding, Promotion, Service anniversary, Recognition

**Opening:**

> Cohort ไหนควรได้รับประสบการณ์เดียวกัน และกลุ่มไหนต้องการ Recognition เพิ่มจาก Welcome kit มาตรฐานครับ

**ต้องค้นหา:**

- Cohort/grade label ที่ HR ยืนยัน
- Join date/event cadence และ repeatability
- Work/Tech/Care constraints
- Manager/Leadership treatment ที่ต่างจาก Staff
- Bulk office delivery เทียบ individual fulfilment

**CTA:** ส่ง cohort/segment, required date และ brand guideline โดยยังไม่ส่งรายชื่อบุคคล

## 11. Offer Route Conversation

Route มีหน้าที่ช่วยตัดสินใจ ไม่ใช่แสดงสินค้าทั้งหมด

### Route A — Core-fit

ตอบ Objective หลักด้วยความซับซ้อนต่ำกว่าและ Operational path ชัด เหมาะเป็น Baseline สำหรับเปรียบเทียบ

### Route B — Experience-led

สร้างความต่างผ่าน Theme, Packaging, Message, Choice หรือ Format ที่ชัดเจน โดยยังอยู่ใน Tier และ Constraint ที่อนุมัติ

### Route C — Strategic alternative

ใช้เฉพาะเมื่อมีความต่างด้าน Treatment หรือ Trade-off จริง เช่น Physical เทียบ Hybrid ห้ามเพิ่มเพียงเพื่อเปลี่ยนสีหรือ SKU เล็กน้อย

### วิธีนำเสนอ

1. ทวน Campaign objective และ Matrix row
2. อธิบาย Treatment logic ก่อน Candidate product
3. แสดง Theme/Format และเหตุผล
4. แสดง Trade-off: ความซับซ้อน, approval, timeline, claim หรือ fulfilment
5. ระบุ Price/MOQ/Lead time/Validity เฉพาะค่าที่ผ่าน Authority
6. แสดง Unknown และ Dependency
7. ขอให้เลือก Direction หรืออนุมัติ Scope สำหรับ Feasibility/Sample

ประโยคใช้งาน:

> สอง Route นี้ไม่ได้แบ่งว่าอันหนึ่งดีอีกอันหนึ่งไม่ดีครับ แต่ตอบความตั้งใจต่างกัน Route A รักษาความเรียบง่ายและแกนร่วม ส่วน Route B เพิ่มความเฉพาะของกลุ่มผ่าน Theme และประสบการณ์ โดยทั้งสองยังต้องผ่านราคาและความพร้อมก่อน Quote

## 12. Proposal Structure

Proposal สำหรับ Multi-Audience ต้องมี:

1. Campaign objective, scope และ version
2. Assumption/Unknown ที่มีผลต่อข้อเสนอ
3. Recipient Matrix ที่ Client ยืนยันหรือระบุสถานะชัด
4. Route A/B และ Route C เฉพาะเมื่อจำเป็น
5. Gift Tier, Theme, Format และ Treatment rationale ต่อ Segment
6. Candidate Component พร้อม Readiness state
7. ราคา จำนวน MOQ, Lead time และ Validity จาก Authority ที่อนุมัติ
8. Sample, Proof, Artwork และ QC path
9. Delivery/Fulfilment scope
10. Claim, Partner, Data และ Operational gates
11. Exclusion, Dependency และ Change control
12. Approval schedule, next action และ expiry

Proposal ที่มีภาพสินค้าแต่ไม่มี Matrix/Route logic เป็น Catalogue response ไม่ใช่ Multi-Audience Proposal

## 13. Commercial Guardrails

- ห้ามใช้ราคาจาก `price_staging` เป็น Quote authority เพียงเพราะมีข้อมูลอยู่
- ห้ามบอก MOQ, Lead time, Stock หรือ Validity โดยไม่มี Source และเวลาที่ตรวจ
- ห้ามคำนวณ Margin หรือ Discount policy จาก Cost workbook ที่ยังไม่ผ่าน Schema/CR และ Commercial approval
- Estimate ต้องมี Label, Assumption, Owner และวันหมดอายุ
- ราคาเดียวกันไม่ได้แปลว่า Treatment ต้องเหมือนกัน; ความต่างอาจอยู่ที่ Message, Packaging หรือ Service แต่ต้องตรวจ Cost-to-serve
- Bespoke ต้องมี Development scope, IP/Artwork right, Sample/revision policy และ Commercial owner
- Voucher/Experience อยู่ในสถานะ `not generally available` จน Partner readiness ผ่าน
- การส่ง Proposal ไม่จอง Stock, Capacity หรือ Production slot เว้นแต่มี Authority ระบุชัด

หากลูกค้าขอราคาทันที:

> ผมสรุปช่วงโจทย์และจำนวนให้ทีมตรวจได้ครับ แต่ขอไม่ยืนยันตัวเลขจนกว่า Product และ Commercial จะตรวจ Spec, MOQ, ระยะเวลา และ validity ของ Route นี้ เพื่อให้ราคาที่ส่งใช้ตัดสินใจได้จริง

---

## 14. Claim and Proof Guardrails

ใช้ Proof ตามลำดับ:

1. Process/Template ที่สาธิตได้
2. ตัวอย่าง Matrix/Route ที่ไม่มีข้อมูลลูกค้า
3. Product/Set ที่ Spec, Price, MOQ และ Lead time ผ่าน Gate
4. Case Study ที่มี Permission
5. ตัวเลขผลงานที่มี Source, Scope, Period และ Claim approval

ห้ามพูดหรือเขียน:

- “MOQ ต่ำที่สุดในตลาด”
- “ทำได้ตั้งแต่ 5 ชิ้น” หาก SKU/Quote ที่อนุมัติไม่รองรับ
- “รักษ์โลก”, “Eco-friendly”, “Reused” หรือ “ลด Carbon” โดยไม่มีหลักฐานระดับสินค้า/Partner
- “เพื่อสุขภาพ” ในความหมาย Medical outcome
- “ปลอดภัย”, “รับรอง” หรือ “ใช้ได้ทุกคน” หากไม่มี Authority
- “ใช้ได้ทุกร้าน/ทุกสาขา” สำหรับ Voucher ที่ Contract/Terms ยังไม่พร้อม
- “เหมาะกับ VIP” จากการอนุมานข้อมูลส่วนบุคคล
- จำนวนลูกค้า ยอดขาย ชิ้นงาน หรืออัตราความสำเร็จที่ Source/Scope ไม่ผ่าน

เมื่อถูกถาม Claim ที่ยังไม่พร้อม:

> แนวคิดนี้อยู่ใน Theme ที่เราคัดได้ครับ แต่ข้อความ Claim ต้องตรวจหลักฐานของสินค้าหรือ Partner ตัวจริงก่อน ผมจะระบุเป็น Direction และกลับมายืนยันถ้อยคำที่ใช้ได้หลัง Review

## 15. Objection Handling

### “ขอดูแคตตาล็อกก่อน”

**ตอบ:**

> ได้ครับ ผมส่งตัวอย่าง Theme ให้ดูได้ แต่ขอทราบโอกาส ผู้รับ และจำนวนคร่าว ๆ ก่อน 3 อย่าง เพื่อคัดเฉพาะตัวที่มีเหตุผลและตรวจความพร้อมได้ จะได้ไม่เสียเวลาเลือกของที่ไม่เหมาะหรือทำไม่ทันครับ

**Next action:** เก็บ Minimum brief แล้วส่ง Curated examples ไม่ส่งรายการทั้งหมดโดยไม่มีบริบท

### “อยากได้ของเหมือนกันทั้งหมด จะได้ง่าย”

**ตอบ:**

> ทำได้ครับ และเราอาจเก็บแกนหลักเดียวกัน แล้วปรับเฉพาะ Packaging, Message หรือ Add-on สำหรับกลุ่มสำคัญ หากไม่มีเหตุผลต้องต่าง เราจะไม่เพิ่มความซับซ้อนครับ

**Next action:** ตรวจว่ามี Treatment difference จริงหรือไม่; ถ้าไม่มี ให้ใช้ Route เดียวอย่างตรงไปตรงมา

### “Signature คือของแพงสำหรับผู้บริหารใช่ไหม”

**ตอบ:**

> Signature คือระดับความตั้งใจและการดูแลครับ ไม่ได้ล็อกว่าต้องเป็นผู้บริหารหรือสินค้าราคาแพง อาจเป็น Key Media หรือ Top-tier Member และเลือก Tech, Care, Taste หรือ Theme อื่นได้ตามผู้รับ

### “มี Tech, Care, Food ให้เลือกได้ไหม”

**ตอบ:**

> ได้ครับ เราใช้เป็น Theme ทางเลือกภายใน Gift Tier เดียวกัน เช่น Signature Care หรือ Signature Tech โดยจะคัด 2 Route ให้เทียบ ไม่ต้องล็อกทั้งแคมเปญไว้ประเภทเดียว

### “ขอราคาถูกที่สุด”

**ตอบ:**

> ช่วยหา Route ที่คุมงบได้ครับ ขอทราบก่อนว่าส่วนไหนห้ามลด—จำนวน, ภาพลักษณ์, Packaging, Message หรือวันส่ง—แล้วเราจะทำ Baseline ที่รักษา Outcome สำคัญไว้

### “ยังไม่รู้ Budget ส่ง Proposal มาก่อน”

**ตอบ:**

> เราทำ Direction และ Matrix ก่อนราคาได้ครับ แต่เพื่อทำ Quote ที่เทียบได้ ขออย่างน้อย Budget basis หรือ Range และผู้มีอำนาจยืนยัน ไม่เช่นนั้นผมจะระบุเป็น Concept ไม่ใช่ Commercial proposal

### “งานด่วนมาก รับปากวันส่งได้ไหม”

**ตอบ:**

> ผมรับวันเป้าหมายไว้ตรวจได้ครับ แต่ยังยืนยันไม่ได้จนกว่า Spec, จำนวน, Artwork, Sample และ Capacity จะผ่าน Feasibility ถ้าเวลาไม่พอ เราจะเสนอ Scope ที่ลดความเสี่ยงหรือแจ้ง no-fit ตรง ๆ

### “ทำจำนวนน้อยมากได้ไหม”

**ตอบ:**

> ต้องตรวจเป็นราย Route และราย SKU ครับ MOQ ไม่ใช่คำสัญญารวมของ SmartGift ผมจะเช็กจำนวนจริงพร้อมรูปแบบพิมพ์และ Packaging ก่อนยืนยัน

### “อยากได้ Eco-friendly”

**ตอบ:**

> เราเปิด Impact Theme ได้ครับ แต่จะใช้คำว่า Eco-friendly หรือ Recycled ได้เมื่อมี Material, Supplier หรือ Certification evidence ของสินค้าจริง หากหลักฐานยังไม่ครบ เราจะอธิบายวัสดุเท่าที่ตรวจได้โดยไม่ขยาย Claim

### “อยากให้ผู้รับเลือก Voucher เอง”

**ตอบ:**

> เป็น Direction ที่ทำได้เมื่อ Partner, สาขา, อายุสิทธิ์, การคืนเงิน, Support และการส่งมอบผ่าน Gate ครับ ช่วงนี้จะระบุเป็น Option และตรวจ Terms ก่อนเสนอเป็นสิทธิ์จริง

### “ส่งรายชื่อ/เบอร์โทรผู้รับให้เลยได้ไหม”

**ตอบ:**

> ช่วง Brief ขอใช้ Segment, จำนวน และกติกาคัดกลุ่มก่อนครับ หากภายหลังต้องส่งรายบุคคล เราจะกำหนด Purpose, ช่องทาง, สิทธิ์เข้าถึง, Retention และวันลบแยกก่อนรับข้อมูล

### “คู่แข่งถูกกว่า”

**ตอบ:**

> ถ้า Spec และ Scope เท่ากันเราควรเทียบตรง ๆ ครับ จุดที่ขอเช็กเพิ่มคือจำนวนกลุ่ม Packaging, Personalization, Proof, Delivery และความเสี่ยงที่รวมอยู่ เพื่อให้เทียบ Total scope ไม่ใช่เฉพาะราคาต่อชิ้น

### “ขอ Option เยอะ ๆ”

**ตอบ:**

> เพื่อให้ตัดสินใจง่าย เราจะเริ่ม 2 Route ที่ต่างกันจริงครับ หากมีสมมติฐานเชิงกลยุทธ์ที่สามค่อยเพิ่ม Route C แทนการส่งหลายสิบรายการที่ตรวจไม่ครบ

## 16. Follow-up Templates

Template เป็นข้อความภายในรอ Sales Owner/Brand approval ก่อนใช้กับบัญชีจริง

### 16.1 หลัง Discovery

> ขอบคุณสำหรับข้อมูลแคมเปญครับ สรุปเบื้องต้นคือ [Campaign objective] มีผู้รับ [จำนวนกลุ่ม] กลุ่ม ได้แก่ [Segment labels] และต้องใช้ภายใน [date] ประเด็นที่ยังต้องยืนยันคือ [unknowns] ขั้นถัดไป SmartGift จะจัด Recipient Matrix ฉบับร่างให้ตรวจชื่อกลุ่ม จำนวน และระดับ Treatment ก่อนคัด Route ครับ

### 16.2 ขอข้อมูลที่ขาด

> เพื่อให้จัด Route ได้โดยไม่ล็อกสินค้าเร็วเกินไป ขอข้อมูลเพิ่ม 4 เรื่องครับ: [segment rule], [count/range], [budget basis], [approval date] ยังไม่ต้องส่งรายชื่อบุคคลในขั้นนี้ครับ

### 16.3 ส่ง Matrix ให้ยืนยัน

> แนบ Recipient Matrix v[version] สำหรับยืนยันโครงสร้างผู้รับและ Treatment direction ครับ การยืนยันรอบนี้ยังไม่ใช่การอนุมัติราคา สินค้า หรือผลิต รบกวนตรวจ [rows/fields] และแจ้งผู้อนุมัติภายใน [date] เพื่อเข้าสู่ Feasibility Review

### 16.4 ส่ง Route เพื่อเลือก Direction

> Route A และ B ตอบ Objective ต่างกันตามที่สรุปใน Matrix ครับ ตัวเลขหรือข้อกำหนดที่มีสถานะ TBD ยังรอ Product/Commercial/Operations ตรวจ ขั้นนี้ขอเลือก Direction หรือระบุสิ่งที่ต้องปรับก่อนทำ Quote/Sample

### 16.5 Hold

> เพื่อไม่ให้ใช้ข้อมูลหรือราคาที่หมดอายุ ขอพักสถานะงานเป็น Hold ตั้งแต่ [date] เนื่องจาก [reason] เมื่อมี [required input/approval] เราจะ Revalidate จำนวน ราคา ระยะเวลา และ Route ก่อนดำเนินการต่อครับ

### 16.6 No-fit

> จากข้อจำกัดปัจจุบัน SmartGift ยังไม่สามารถรับปาก Scope นี้โดยไม่ข้าม [gate] ได้ครับ เงื่อนไขที่ทำให้ประเมินใหม่ได้คือ [scope/date/evidence/owner change] จึงขอปิดรอบนี้เป็น No-fit แทนการส่งข้อเสนอที่เสี่ยงทำไม่ได้

|---|---|---|---|
| `ACCOUNT_SELECTED` | ตรวจ Fit และสิทธิ์ติดต่อ | Account source, owner, use-case hypothesis | Owner อนุมัติ Outreach |
| `DISCOVERY_SCHEDULED` | ยืนยัน agenda/participants | Contact basis, meeting record | วันนัดชัด |
| `DISCOVERY_COMPLETE` | บันทึก Brief/Unknown | Discovery note | ผ่าน Qualification Gate |
| `MATRIX_DRAFTED` | สร้าง Matrix version | Brief + source status | Client ยืนยัน Segment/Tier direction |
| `FEASIBILITY_REVIEW` | ขอ Route/Product checks | Approved Matrix version | อย่างน้อย 2 Route ผ่าน หรือ No-fit |
| `PROPOSAL_SENT` | ส่ง Approved proposal | Proposal, validity, approval evidence | Decision owner + next date |
| `DECISION` | บันทึก Won/Lost/Hold | Authority evidence + reason | ส่ง Delivery หรือ Close |
| `DELIVERY` | ประสาน Scope ที่อนุมัติ | PO/contract/proof/checklists | Acceptance evidence |
| `REVIEWED` | ทำ Retrospective | Outcome, effort, feedback | Go/Revise/Stop recommendation |

### Lost Reason Vocabulary

- `PRICE`
- `TIMING`
- `NO_FIT`
- `NO_DECISION`
- `COMPETITOR`
- `OPERATIONAL_CONSTRAINT`
- `CLAIM_OR_COMPLIANCE`
- `DATA_OR_PRIVACY`
- `UNKNOWN`

ทุกสถานะต้องมี Account owner, last action, next action/date หรือ closure reason ห้ามปล่อย Proposal ค้างแบบไม่มีเจ้าของ

## 19. Escalation and Stop Conditions

หยุดการรับปากและ Escalate เมื่อ:

- ลูกค้าต้องการข้าม Feasibility/Sample/Claim gate
- ราคา Source หรือ Validity ขัดกัน
- Count, Spec หรือ Timeline เปลี่ยนหลัง Approval
- Supplier/Partner ไม่ยืนยัน Capacity หรือ Terms
- มีคำขอ Medical, Sustainability, Certification หรือ Impact claim ที่ไม่มี Evidence owner
- ต้องรับ PII/Sensitive data ก่อน Privacy boundary พร้อม
- บุคคลหนึ่งต้องอนุมัติทั้ง Classification, Price และ Claim ของงานตัวเองโดยไม่มี Separation
- Proposal ถูกส่งจาก Version ที่ไม่ใช่ Matrix ล่าสุด
- มีแรงกดดันให้เรียก Verbal interest ว่า Won
- Scope Bespoke ไม่มี IP, revision, design fee หรือ ownership boundary

สถานะที่ใช้: `HOLD_FOR_REVIEW`, `REQUOTE_REQUIRED`, `RECONFIRM_MATRIX`, `NO_FIT`, `CANCELLED` ตามเหตุผลจริง

## 21. Rehearsal Scenarios

ก่อน Controlled outreach ทีมต้อง Dry run อย่างน้อย 3 สถานการณ์:

### Scenario A — Member หลาย Tier

- Core Member + Top-tier Member
- ลูกค้าต้องการเปิด Tech, Care และ Taste โดยไม่ล็อก
- Budget range ยังไม่อนุมัติ
- ตรวจว่า Sales ทำ Matrix และขอ Budget basis โดยไม่ขอ PII ได้

### Scenario B — Launch/Media

- General Media + Key Media + Event Guest
- Event date กระชั้นและมีคำขอ Eco claim
- ตรวจว่า Sales ไม่จัดอันดับสื่อเอง ไม่รับปากวันส่ง และ Escalate Claim evidence

### Scenario C — Employee Welcome

- Staff + Manager + Leadership
- ลูกค้าขอของเหมือนกันทั้งหมด แต่ต้องการให้ Leadership รู้สึกพิเศษ
- ตรวจว่า Sales เสนอ Shared core + treatment variation โดยไม่เพิ่มความซับซ้อนเกินจำเป็น

### Rehearsal scoring

ใช้ `PASS / NEEDS REVISION / STOP` ต่อหัวข้อ:

- Positioning accuracy
- Discovery completeness
- Dimension separation
- Unknown handling
- Commercial/claim truthfulness
- Privacy boundary
- Matrix handoff
- Next-action clarity

ไม่มีการกำหนด Target ตัวเลขจน Sales Owner อนุมัติ Measurement definition และ Baseline

## 22. Coaching and Review Cadence

ก่อน Pilot Owner อนุมัติ Cadence จริง ให้ใช้เป็นกรอบเสนอ:

- Pre-call review สำหรับบัญชี/แคมเปญที่มีความเสี่ยง
- Discovery note review ก่อนทำ Matrix
- Matrix clinic เพื่อ Resolve Relationship/Tier/Theme disagreement
- Feasibility huddle ระหว่าง Sales, Product และ Operations
- Proposal preflight ก่อนส่ง
- Won/Lost/Hold review โดยไม่ตีความ Verbal interest เกินจริง
- Pilot retrospective แยกตาม Play, Tier, Theme, Format และ Risk

Review record ต้องมี Version, Evidence, Decision, Owner และ Due date

## 23. Privacy and Record Boundary

- Account list, Contact details, Purchase history และ Recipient list ต้องอยู่ใน Local/authorized system ไม่อยู่ใน Git
- Playbook และ Template กลางใช้ข้อมูลสมมุติเท่านั้น
- Discovery note เก็บเท่าที่จำเป็นต่อ Campaign และสิทธิ์เข้าถึงต้องสัมพันธ์กับบทบาท
- Recipient Matrix ใช้ Aggregate count และ Client rule ไม่เก็บชื่อบุคคล
- ถ้าต้อง Fulfil รายบุคคล ต้องมี Manifest แยก พร้อม Purpose, Transfer, Access, Retention และ Deletion
- ห้ามใส่ Cost, Internal margin, Supplier confidential term หรือ Source path ใน Proposal ลูกค้า
- Case Study ต้องมี Permission สำหรับชื่อ โลโก้ ภาพ ข้อมูล และผลลัพธ์แต่ละประเภท

## 24. Acceptance, Success and Exit Criteria

### Acceptance Criteria ของ Playbook

- Talk track สอดคล้องกับ Positioning และ Portfolio Architecture
- รองรับ 3 Pilot Plays และ Buyer roles หลัก
- Discovery ส่งต่อไป Recipient Matrix ได้โดยไม่เดาข้อมูล
- Route/Proposal process อ้าง Product Taxonomy readiness
- Objection handling ไม่สร้าง Unsupported price, MOQ, claim หรือ timeline promise
- มี Privacy, Approval และ Stop boundary ชัดเจน

### Success Criteria ของ Dry Run

- ผู้ขายอธิบาย Signature เป็น Treatment ไม่ใช่ Product/Recipient category
- ผู้ขายแยก Relationship, Client Segment, Gift Tier, Theme และ Format ได้
- ผู้ขายสร้าง Matrix draft จาก 3 Scenario โดยไม่มี PII
- ทุก Unknown มี Owner/Next action หรือถูก Stop
- ไม่มี Route ต่ำกว่า Required readiness หลุดสู่ Proposal simulation
- ผู้ Review สาวคำพูดด้านราคา/Claim/Timeline กลับ Authority ได้

### Exit Criteria ก่อน Controlled Use

- Sales Playbook v0.1 ได้รับอนุมัติ
- Sales Owner, Pilot Owner และ Functional approvers ได้รับการแต่งตั้ง
- Controlled account list และ Outreach channel ได้รับอนุมัติ
- Dry run 3 Scenario ผ่านตามเกณฑ์ที่ Owner รับรอง
- Sales assets, Brief, Matrix, Route comparison และ Proposal template ใช้ Version ที่อนุมัติ
- Measurement definition, data location และ access boundary พร้อม
- Stop/escalation path ได้รับการทดสอบ
