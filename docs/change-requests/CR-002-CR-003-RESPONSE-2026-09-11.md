# Response to CR-002 and CR-003 — 2026-09-11

## Read this first

CR-002 ("Multi-Tier Scope Chain to Zuri Edge Device, GKS & MSP Catalog Vault
Resolution") and CR-003 ("5-Stage Data Pipeline Governance Dashboard,
Ingestion Lanes & Approval Gates UI"), **as written, will not be adopted.**

They are superseded by a **PROPOSED** ADR-075 in `zuri-ai` (not yet written as
a numbered file, not yet approved by the owner — the number is reserved by
this response, no `ADR-075-*.md` exists in `zuri-ai/docs/decisions/` as of
this writing):

> SmartGift's catalog enters GenesisBlockDB only through the 17-stage
> pipeline (`docs/KNOWLEDGE-INGESTION-17-STAGE-FLOW.md`), via a **structured-record
> source adapter that enters before Stage 1**. SmartGift's own 5-stage
> pipeline (`01_raw → 02_prepared → 03_staging_sql → 04_review_reports` plus
> `vaults/`) remains the **source producer** — it prepares and hashes the
> record, it does not gain a second, parallel route into Genesis. Edge reads
> the **published generation** that the 17-stage pipeline produces; it does
> not open a direct Edge→GenesisBlock write path, and it does not maintain a
> second embedding space alongside the pipeline's pinned one.

**The owner has not yet approved ADR-075.** This document states the
zuri-ai-side reasoning and the governing decisions that already exist; it is
not a ratification of anything, and CR-002/CR-003 are not closed by it — only
answered.

## What stays valid

These parts of CR-002/CR-003 describe real, still-correct constraints. Nothing
below is in dispute.

| From CR-002 / CR-003 | Why it stays valid |
|---|---|
| **SHA-256 versioned registry as source identity** (`data-pipeline/01_raw/archive/`, `manifest.json` input hashes) | This is exactly how the 17-stage pipeline's Stage 1 (`RawExternalRecord`) and the edge v4 store's own `manifest.json` already establish provenance — hash-pinned inputs, not filenames or timestamps. Directly compatible with a structured-record adapter. |
| **Zero-PII invariant in the product/catalog vector vault** | Correct and unchanged — and now enforced structurally rather than only by convention: Stage 5 (`classify`) of the 17-stage flow is a real gate a personal-data record has to clear before it can reach a vector space at all, not a rule stated in a boundary doc and trusted to hold. |
| **Tri-Source reconciliation flow** (identity review + FlowAccount export + catalog JSON, each hashed and merged) | This is SmartGift-side pipeline design and is untouched by the adapter question — the edge v4 `manifest.json` already records all three inputs (`identity`, `flowaccount`, `catalog`) plus `categoryMap`/`aliases`, each with a `sha256`, confirming the pattern is already live. |
| **Price authority remaining in SmartGift** (FlowAccount export as canonical price source, `pricing_calculator.py`) | Not a knowledge-ingestion concern at all — the 17-stage pipeline and any GenesisBlock vault never become a price authority. CR-002 §4 and `ZURI_ECOSYSTEM_BOUNDARIES.md` §3.5 are both correct here and neither is touched by ADR-075. |
| **ADR-006 private-repo allowlist** (9 intake/copy files + 4 cost workbooks in private `Freshair129/TN001B01-SmartGift` only) | Independent of CR-002/CR-003 and independent of ADR-075. Still governs; still narrow; still does not approve a Files-tab/CRM sync path (CR-006 §"Current policy amendment"). |

## What SmartGift is asked to do

1. **Keep producing prepared JSON + registry hashes** exactly as the 5-stage
   pipeline does today — `data-pipeline/02_prepared/pricelist_master.json`,
   the `01_raw/archive/` SHA-256 archive, and the tri-source hashes recorded
   in the edge `manifest.json` (`identity`, `flowaccount`, `catalog`,
   `categoryMap`, `aliases`). This is the shape a structured-record source
   adapter needs and nothing about it changes under ADR-075.
2. **Stop treating `vaults/vlt-catalog-product/genesis-db` as a store any
   other system reads.** CR-002/§3.C and `ZURI_ECOSYSTEM_BOUNDARIES.md` §3.2
   already say the edge's own `genesis_smartgift_store_v4` must not be written
   by outside agents; the same isolation should now run the other way too —
   `vlt-catalog-product` is SmartGift's own local substrate (currently a
   1024-dim `default`-model collection per its `state.json`, observed below),
   not a vault GKS, MSP or the edge pipeline is expected to resolve into or
   query directly.
3. **Update `README`/`ZURI_ECOSYSTEM_BOUNDARIES.md` to drop the non-existent
   APIs** — `API-010 msp_vault_resolve` (not present in either side's actual
   contract per CR-006 §4), `query-ir.v1`, the `R0–R6` radius scheme, and the
   `D:\` canonical paths — so the boundaries document describes what is
   actually wired rather than a design that was never built.

## Open questions for the owner

1. **Approve ADR-075?** — the structured-record-adapter framing above is
   this session's reasoning, not a ratified decision. Until the owner
   approves it (or a revision of it), CR-002/CR-003 stay "proposed" and
   ADR-075 stays unwritten as a numbered file.
2. **Sibling-checkout file read vs. `FileAsset` upload** — today's edge v4
   pipeline reads `pricelist_master.json` straight off disk from a sibling
   checkout (`apps/edge/src/rag/v4/paths.ts` default, overridable via
   `SMARTGIFT_UPSTREAM_PRICELIST`). A structured-record adapter into the
   17-stage flow could instead go through `zuri-ai`'s existing `FileAsset`
   admission path. Which one should the adapter target — keep the
   sibling-checkout read (simple, but ties ingestion to one machine's
   directory layout) or move to an authenticated `FileAsset` upload (fits the
   admission/ACL/audit model the rest of Stage-0 uses)?
3. **How long does edge v4 stay as a fallback?** The edge device currently
   runs its own independent v4 store and `:8888` RAG service, generated
   straight from the SmartGift prepared files, entirely outside the 17-stage
   flow. If ADR-075 is approved, is edge v4 retired once the adapter is live,
   kept as an offline/degraded-connectivity fallback, or kept indefinitely
   for latency reasons? This changes whether `paths.ts` and
   `scripts/rag-serve.ts` are in scope for the adapter work or stay as-is.
